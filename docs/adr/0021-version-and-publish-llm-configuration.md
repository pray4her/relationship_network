# LLM 调用绑定在线更新形成的不可变配置版本

每个职位需求解析任务绑定一个数据库中的 LLM 配置版本，该版本不可变地记录任务类型、OpenRouter、模型名称、生成参数、隐私路由策略和提示词版本；在线更新只影响之后创建的任务，历史任务始终保留原配置。OpenRouter API 密钥和端点等部署秘密仍由 `RN_` 环境配置提供且不入库；初始迁移创建默认模型为 `x-ai/grok-4.5` 的配置。相比直接从可变模型环境变量读取，这一选择避免运维重启静默改变任务行为，并保留模型切换的完整历史。

配置版本同时记录单次请求超时，默认 180 秒，平台管理入口只接受 30 至 300 秒。超时变更只影响绑定新配置版本的后续任务，历史任务和自动重试继续使用原值。

Issue #11 同时交付最小的平台管理配置入口：平台管理员可查看历史版本并直接在线修改当前配置；提交保存后先创建持久化的 LLM 配置变更尝试并返回 `202`，后台探测成功且并发检查通过时，在同一事务中创建新的不可变版本并立即设为当前版本。不设置可编辑配置草稿、回归评估或单独发布步骤。旧版本不可编辑或删除，每次变更尝试及其结果都写入平台审计记录；后端授权沿用独立的平台管理员与强制 MFA 边界，并提供最小可用管理界面，而不是要求运营人员直接修改数据库。

平台管理界面通过单个 LLM 配置变更尝试对应的一条 SSE 流接收异步进度，不使用轮询，也不与租户职位解析事件混流。平台事件表使用从 1 开始的连续事件序号并只增保留，状态转换与事件同事务提交；SSE 支持 `Last-Event-ID`，单次连接最长 60 秒并重新执行平台管理员与 MFA 授权，发送 `succeeded`、`failed`、`conflicted` 或 `cancelled` 后关闭。PostgreSQL `NOTIFY` 仅作实时唤醒，事件正文仍从数据库读取。

提示词模板以仓库内版本化文件管理，每个版本具有稳定标识和内容哈希，并与严格 JSON Schema、字段目录、测试和代码部署共同发布。平台管理员只能在 LLM 配置中选择应用已存在的提示词版本，不能在线编辑模板正文；单次调用仍不保存由模板与业务输入组装出的完整提示词。

提示词版本文件采用追加式管理：一旦被 LLM 配置或解析任务引用，其内容不得修改或删除，并必须继续随应用部署，以保证绑定旧配置的任务能够使用原提示词自动重试。任何提示词调整都新增版本标识和文件；CI 校验版本标识唯一、文件内容哈希与清单一致，并拒绝已登记版本发生原地变更。

每个提示词版本在清单中声明唯一兼容的职位需求 Schema 版本。保存 LLM 配置前，后端先校验所选提示词、严格 JSON Schema 和业务校验器属于同一 Schema 版本；不匹配时直接拒绝，不执行 OpenRouter 探测，也不创建配置版本或 LLM 调用记录。

系统不维护独立的当前职位需求 Schema 指针。当前 LLM 配置通过所选提示词唯一确定用于新解析任务的 Schema 版本，并将模型、提示词和 Schema 作为一个配置版本原子启用；历史任务继续使用其绑定的旧配置组合。

ZDR、拒绝数据采集、要求上游支持全部结构化参数以及禁止跨模型自动回退是系统强制约束，不作为可编辑配置字段，也不在平台管理界面提供关闭选项。平台管理员只能修改模型、受支持的生成参数和已有提示词版本；保存后的请求仍必须由适配器注入全部强制路由约束。

平台管理入口不接受任意生成参数 JSON。首期白名单仅包含 `temperature`（默认 0，范围 0 至 1）、`max_output_tokens`（默认 8192，范围 1024 至 16384）和 `request_timeout_seconds`（默认 180，范围 30 至 300）；模型和提示词版本使用独立字段选择。`stream`、响应 Schema、隐私路由和回退策略始终由适配器强制，不能通过白名单参数覆盖。

OpenRouter 可以在满足上述全部系统约束的上游供应商之间进行路由或故障回退，但整个任务及其所有自动重试必须使用配置版本中相同的模型标识，不得切换到其他模型。每次调用记录 OpenRouter 实际选用的上游供应商；没有合规上游可用时按任务错误与重试策略处理，不放宽隐私或参数约束换取成功。

职位需求解析和配置能力探测都固定使用非流式 OpenRouter 响应 `stream=false`。系统不消费或展示模型生成中的 Token 或半成品 JSON；只有完整响应通过严格 JSON Schema 与业务校验后才可产生职位需求草稿。SSE 只传递持久化的任务生命周期事件，不承载模型输出增量。

LLM 配置变更尝试使用不含业务数据的固定输入和严格 JSON Schema 对 OpenRouter 异步执行一次最小能力探测；模型不存在、没有满足强制路由约束的端点或不支持所需参数时将尝试置为失败，探测成功后立即创建并启用新版本。该探测只验证可调用性，不评价职位需求解析质量，也不产生或要求 LLM 回归评估记录。

配置变更尝试复用解析任务的调用重试规则：所有可重试错误共享最多 3 次实际 OpenRouter 调用，结构无效响应最多 2 次，每次调用独立记录；退避期间进入 `retry_scheduled` 并持久化 `next_attempt_at`，由数据库调度与 Outbox 重新排队。所有重试绑定同一候选配置快照，不切换模型或放宽强制约束，也不计入租户额度或租户技术限流。每次重试前若预期当前配置已经变化，则直接终结为 `conflicted`，不再调用 OpenRouter。

最小能力探测属于必须审计的实际 LLM 调用。无论探测成功还是失败，都创建一条平台级 `config_probe` 调用记录，记录候选配置指纹、模型、提示词版本、调用结果和平台成本；该记录不关联租户或职位需求解析任务。探测失败时不创建正式 LLM 配置版本，但探测调用记录和平台审计事实必须保留。

每个 LLM 配置变更尝试长期保留一份不可变的候选配置 JSONB 快照，包含实际参与探测的模型、生成参数、提示词版本和系统强制路由策略，但排除 API Key、端点凭据及其他部署秘密。失败探测的候选快照只表示平台管理员执行过的变更尝试，不构成配置草稿，不可编辑、发布或自动转为当前配置。

平台管理员提交配置变更尝试时必须携带其读取时的当前配置版本 ID；提交时已经过期则同步返回 `409`，不创建尝试。能力探测成功后，后端在创建并切换新配置版本的事务中再次以该 ID 执行比较交换；探测期间当前版本已经变化时，将异步尝试置为 `conflicted`，不创建或启用候选配置版本，禁止后提交者静默覆盖其他管理员的修改。冲突发生前已经完成的探测调用、候选快照和平台审计事实继续保留。

全平台至多存在一个 `queued`、`running`、`retry_scheduled` 或其他非终态的 LLM 配置变更尝试，由数据库部分唯一索引强制。已有尝试未终结时，新的提交返回 `409 config_change_in_progress` 和现有尝试 ID，不创建候选快照、Outbox 或探测调用；前一个终结后，管理员必须基于最新当前配置版本重新提交。

平台管理员可以取消 `queued`、`running` 或 `retry_scheduled` 的配置变更尝试；运行中取消先进入 `cancel_requested`，Worker 在安全点停止后进入 `cancelled`。已经发出的探测调用及平台成本继续保留，但任何迟到结果都不得创建或启用配置版本；只有尝试进入终态后才允许提交新的配置变更。

LLM 配置变更尝试与职位需求解析任务复用内部 Outbox、Dispatcher、租约与心跳、退避调度、只增状态事件和 SSE 辅助模块，但使用独立的平台业务表与授权策略。系统不建立混合租户任务和平台任务的多态“万能任务表”，避免作用域与 RLS 规则相互污染。

自动化测试通过仓库内假 OpenRouter 服务验证配置探测成功、失败、重试、取消和并发冲突，不使用真实 API 密钥。真实 OpenRouter 的当前可调用性只由平台管理员提交配置变更尝试时执行的最小能力探测确认；CI 假服务不替代该线上探测，也不构成回归评估。

回退历史配置不直接重新指向或重新启用旧版本。平台管理员选择历史版本后，系统复制其中不含秘密的参数形成新的候选配置，重新执行最小能力探测，并在通过乐观并发检查后创建新的不可变配置版本并设为当前；新版本记录来源历史版本 ID，旧版本及原生效时间线保持不变。
