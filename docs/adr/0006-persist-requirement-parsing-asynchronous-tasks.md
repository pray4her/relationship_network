# 职位需求解析使用持久化异步任务

提交职位需求输入快照后，API 先持久化职位需求解析任务并立即返回，由异步 Worker 将任务从 `queued` 推进到 `running`；需要退避时进入 `retry_scheduled`，最终进入 `succeeded`、`failed` 或 `cancelled`，运行中的取消先经过 `cancel_requested`。重试属于同一任务的后续尝试，只有成功且通过结构校验的结果才能产生职位需求草稿。任务记录是业务状态的事实源，Celery 和 Redis 只负责投递与执行，因此浏览器断线、请求超时或 Worker 重启不会丢失任务状态或误生成职位需求草稿。

同一职位至多存在一个 `queued`、`running`、`retry_scheduled` 或 `cancel_requested` 的职位需求解析任务，并由数据库约束守住这一并发边界。重复提交同一幂等键返回原任务；输入不同但已有任务未结束时拒绝新提交，避免先发任务较晚完成并产生相互竞争的职位需求草稿。

幂等键在租户范围内由数据库唯一约束强制，并与完整有效请求指纹绑定。指纹覆盖职位、输入快照正文与来源顺序、来源标识及任务绑定的 LLM 配置版本；同一键和同一指纹返回原任务，同一键但指纹不同返回 `409 idempotency_conflict`。冲突不计入技术限流，也不创建输入快照、解析任务、Outbox 事件或 LLM 调用记录。

只有 `draft`、`active` 或 `closed` 状态的职位可以创建解析任务；`archived` 职位只允许读取历史任务和结果，不得创建、重新解析或恢复新的业务执行。

职位归档时不等待非终态解析任务结束。归档事务将 `queued` 或 `retry_scheduled` 任务直接置为 `cancelled`，将 `running` 任务置为 `cancel_requested`；Worker 在下一安全点停止并将其置为 `cancelled`。外部请求已经发出时仍保留独立 LLM 调用、原始响应和成本元数据，但其结果只能用于审计，不得生成或替换职位需求草稿。

具有 `jobs:manage` 权限且租户可写的成员可以主动取消 `queued`、`running` 或 `retry_scheduled` 解析任务，使用与归档相同的 `cancel_requested`/`cancelled` 状态转换。取消操作幂等并写入租户审计事件；原职位需求草稿保持不变，已经发出的外部请求与成本仍按调用审计规则记录，但响应不得写入草稿。只有任务进入 `cancelled` 终态后才能创建新的解析任务。

职位需求解析进度通过 Server-Sent Events（SSE）从服务端单向推送到浏览器，不为 Issue #11 引入 WebSocket。SSE 连接沿用现有 HttpOnly 会话 Cookie、租户身份与 `jobs:read` 授权；创建任务、取消任务和读取当前状态仍使用普通 HTTP API。浏览器断线后可重新建立连接，刷新页面时始终以数据库中的持久任务状态为事实源。

每个解析任务使用从 1 开始的连续事件序号，并将业务状态事件写入只增的职位需求解析任务事件表。任务状态转换与对应事件必须在同一个 PostgreSQL 事务中提交；SSE 接口按 `Last-Event-ID` 读取缺失事件后继续推送，因此进程重启或短暂断线不会丢失业务状态变化。事件表受租户 RLS 约束，应用角色仅有 `SELECT/INSERT` 权限，不得更新或删除。

持久事件只包含租户可见的任务状态、稳定错误分类、可重试性和时间，不包含原始 LLM 响应、供应商诊断或平台成本。保持连接所需的 SSE 心跳不写入事件表，也不占用业务事件序号。

事务提交业务事件时同时发送 PostgreSQL `NOTIFY` 作为 SSE 服务的非持久实时唤醒信号，不使用 Redis Pub/Sub 复制事件正文。通知载荷只包含职位需求解析任务 ID 和事件序号；SSE 服务收到通知后仍必须在当前会话的租户 RLS 上下文中读取事件表。通知丢失、监听连接重启或 API 实例切换不影响正确性，服务通过客户端的 `Last-Event-ID` 和持久事件表补读缺失事件。

SSE 使用单个职位需求解析任务作为连接与授权边界，不提供租户级混合任务流。客户端一次只订阅职位详情页的当前任务，事件 ID 即该任务的连续事件序号；服务端发送 `succeeded`、`failed` 或 `cancelled` 终态事件后主动结束连接。

单次 SSE 连接最长保持 60 秒，连接期间每 15 秒发送一次不落库、不占业务事件序号的心跳；达到上限时服务端正常结束连接，浏览器携带 `Last-Event-ID` 自动重连并重新执行会话认证、`jobs:read` 授权与租户 RLS 初始化。任务进入终态时立即发送终态事件并关闭连接，不等待连接期限，以使会话撤销、成员停用和权限变更最迟在下一次重连时生效。

职位需求解析任务及其只增业务事件长期保留，不设置独立清理期限。90 天保留期只清理既定范围内未绑定确认版本的输入全文和加密原始响应，不删除任务身份、状态历史、事件、LLM 调用核心、结果事件或元数据补齐事件；SSE 心跳从不持久化。

OpenRouter 返回成功响应但内容未通过职位需求结构校验时，同一任务自动重试一次；第二次仍无效则进入 `failed`。每次尝试都保留审计元数据和加密原始响应，但任何未通过校验的响应都不得产生职位需求草稿。

结构无效、网络错误、限流、超时和 `outcome_unknown` 共享每个解析任务最多 3 次实际 OpenRouter 调用的总预算，同时结构无效响应最多允许 2 次。所有已经发出的不确定调用都计入总预算；在请求发出前识别出的永久配置、认证或隐私路由错误不占实际调用次数，但任务立即失败。不同错误类型交替出现不得重置或叠加调用预算。

网络错误、超时、限流以及 OpenRouter 或上游服务端错误最多执行三次（首次加两次重试），优先遵守服务端重试等待时间，否则采用带抖动的指数退避。等待期间任务进入 `retry_scheduled` 并持久化 `next_attempt_at`，到期后再进入 `queued`；请求、认证、余额、隐私路由或参数支持等永久错误立即失败。所有重试都绑定相同的职位需求输入快照、模型和配置版本，不得通过自动切换模型换取成功。

数据库清扫任务负责领取 `next_attempt_at <= now()` 的 `retry_scheduled` 任务，并在同一个事务中将其切回 `queued`、追加任务业务事件并写入新的 Outbox 事件。不得使用 Celery 长时间 ETA 消息作为计划重试的事实源；清扫和 Outbox 投递可安全重复执行，数据库约束保证同一次到期转换只生成一个有效排队事件。

解析任务状态转换矩阵由数据库强制，并由条件更新同时校验当前状态与租约令牌：`queued` 只能进入 `running` 或 `cancelled`；`running` 只能进入 `retry_scheduled`、`succeeded`、`failed`、`cancel_requested`，或在租约确认过期时恢复为 `queued`；`retry_scheduled` 只能进入 `queued` 或 `cancelled`；`cancel_requested` 只能进入 `cancelled`。`succeeded`、`failed` 和 `cancelled` 均为不可逆终态。

数据库部分唯一索引覆盖 `queued`、`running`、`retry_scheduled` 和 `cancel_requested`，强制同一租户内每个职位最多一个非终态解析任务。服务层检查仅用于返回友好错误，不能代替数据库并发约束。

职位需求解析任务与平台 LLM 配置变更尝试复用内部异步编排组件，包括 Outbox、Dispatcher、租约与心跳、退避调度、只增状态事件和 SSE 辅助模块；职位解析仍使用独立租户业务表和 RLS，不与平台任务合并为多态任务表。

CI 不调用真实 OpenRouter。仓库内提供可编程的假 OpenRouter 服务，覆盖严格成功、结构无效、429、5xx、超时、迟到响应和元数据延迟，并在真实 PostgreSQL、Redis、Worker 与 SSE 链路中验证重试预算、Outbox、RLS、取消和草稿原子提交；测试不需要真实 API 密钥，也不产生外部成本。

创建、取消和用户重新发起解析，编辑或放弃职位需求草稿，解决来源冲突，执行 Schema 升级以及确认职位需求版本等全部写操作都记录租户审计事件，不要求成员填写原因。事件只保存操作类型、对象 ID、成员、时间与结果，不复制输入全文、完整结构化 JSONB、提示词或原始 LLM 响应；普通读取不记录，平台原始响应查看继续使用单独的平台审计规则。

已认证且已经进入业务写路径的校验失败、乐观锁冲突、幂等冲突和业务状态拒绝也必须形成失败审计事件，并通过独立提交保证业务事务回滚时事件仍保留。未认证请求以及因 RLS 对调用者表现为对象不存在的跨租户访问不记录包含目标资源事实的事件，避免审计副作用泄露资源是否存在。

单次 OpenRouter 请求使用任务所绑定 LLM 配置版本中的超时值，默认 180 秒，平台管理员只能在 30 至 300 秒范围内调整。请求超时按可重试瞬时错误处理并计入原任务尝试上限；请求等待期间 Worker 继续更新心跳，任务租约和执行时限必须大于配置的请求超时及必要收尾余量，不能把仍在等待的有效请求误判为失联。

每个职位至多有一个当前可编辑的职位需求草稿。已有草稿时重新解析必须由用户明确确认替换；旧草稿在新任务成功前继续有效，新任务失败时保持不变，只有新任务成功并通过结构校验后才原子替换，避免重新解析失败导致用户修改丢失。

数据库部分唯一索引以 `(tenant_id, job_id)` 强制每个职位最多一个 `editable` 草稿。草稿被确认、被成功解析结果替换或由成员放弃时，分别进入 `confirmed`、`replaced` 或 `abandoned` 终态并保留历史身份；解析成功替换时在同一事务中终结旧草稿并创建新草稿，不能短暂出现两个当前可编辑草稿。

职位需求草稿使用单调递增的修订号进行乐观并发控制。更新和确认必须携带读取时的修订号；修订号已变化时返回明确冲突，要求成员刷新后重新应用修改，不允许最后写入者静默覆盖其他成员的条件调整。

放弃当前草稿同样必须携带读取时的修订号，并沿用 `jobs:manage` 与可写租户门禁。存在 `queued`、`running`、`retry_scheduled` 或 `cancel_requested` 的替换解析任务时禁止放弃；操作成功后草稿进入 `abandoned`，不修改职位当前确认版本。

替换草稿的职位需求解析任务处于 `queued`、`running`、`retry_scheduled` 或 `cancel_requested` 时，旧草稿保持可查看但暂时禁止编辑和确认。任务失败或取消后恢复旧草稿编辑，任务成功后原子切换到新草稿，避免任务结果覆盖运行期间发生的修改或确认。

职位需求解析不消耗租户业务额度，但使用独立的技术限流控制平台成本：默认每个租户最多同时运行 2 个 `running` 解析任务、每小时最多新建 20 个，阈值由平台配置调整；`queued` 和 `retry_scheduled` 不占运行槽，但仍受每个职位一个非终态任务约束。重复幂等请求不计数；超限返回 `429`，不创建任务、不投递消息，也不调用 OpenRouter。

系统策略触发的自动重试属于原职位需求解析任务，继续绑定原输入快照和原 LLM 配置版本。用户对终态失败任务发起“重新解析”时创建关联原任务的新任务，复用原输入快照但绑定操作当时的当前 LLM 配置版本，以便配置修复后重新执行并保留清晰的业务尝试历史。

Celery 消息同时携带租户 ID 和职位需求解析任务 ID；Worker 使用普通应用数据库角色，先设置 `app.tenant_id`，再按租户与任务双重条件加载数据，不获得 RLS 绕过能力。平台管理员的跨租户诊断仍使用现有 `app.platform_admin` 显式放行路径。

创建职位需求解析任务时，API 在同一个 PostgreSQL 事务中同时写入任务记录和待投递的 Outbox 事件，不在事务提交后直接调用 Celery。独立 Dispatcher 读取并投递 Outbox 事件；事件只有在成功提交给 Celery 后才标记为已投递，失败时可安全重试，避免任务已经提交但消息丢失并永久停留在 `queued`。

Outbox 投递只保证至少一次交付。Worker 必须以职位需求解析任务记录为事实源，通过任务状态和数据库行锁幂等认领消息；重复或延迟消息不得重复执行已经完成的任务，也不得额外创建 LLM 调用记录。Outbox 表继续受租户 RLS 约束，普通 API 和 Worker 不能跨租户扫描。

独立 Outbox Dispatcher 数据库角色只允许调用固定的 `claim_outbox_batch` 函数，原子领取待投递事件的最小字段 `tenant_id`、任务 ID 和事件 ID，不具有任意查询业务表或 Outbox 正文的权限。Dispatcher 只负责向 Celery 投递；Worker 收到消息后仍必须设置 `app.tenant_id` 并按租户 RLS 读取任务，不能把 Dispatcher 的受限领取能力传递给执行路径。

Worker 认领任务时在数据库中写入有期限的执行租约，并在执行期间定期更新心跳。清扫任务只能在设置相同租户 RLS 上下文后，通过数据库行锁确认任务仍为 `running` 且租约已经过期，再将同一个职位需求解析任务重新排队；不得通过创建新业务任务来恢复执行。

崩溃恢复后的执行沿用原任务、输入快照、LLM 配置版本和自动重试上限，但新的外部请求仍须写入新的独立 LLM 调用尝试记录。租约尚未过期、已被其他 Worker 续租或已进入终态的任务不得被重复执行。

外部请求已经发出，但 Worker 在持久化响应前崩溃、超时或失去连接，且无法确认 OpenRouter 是否完成处理时，将该次调用记为 `outcome_unknown`。只要原任务仍有剩余自动重试次数，恢复后的 Worker 就自动发起新的独立调用；新调用计入原任务既定重试上限，不假设 OpenRouter 能按客户端请求标识去重，也不把可能重复产生的平台成本计入租户额度。

不确定调用稍后返回、重复投递或恢复调用同时完成时，只有持有有效任务租约并通过数据库原子状态转换的有效结果可以生成或替换职位需求草稿。其余响应只保留调用事实与审计数据，不得生成第二份草稿或覆盖已经提交的业务结果。
