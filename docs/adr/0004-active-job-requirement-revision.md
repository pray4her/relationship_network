# 启用中的职位可准备并切换新的职位需求版本

启用中的职位可以在保持 `active` 的同时创建和修改职位需求草稿；未确认草稿不影响当前职位需求版本，确认后产生新的不可变职位需求版本，并成为后续匹配使用的当前版本，历史匹配仍绑定原版本。要求先关闭职位再修改的方案会把需求修订与职位状态及活跃职位额度不必要地耦合，并造成业务中断，因此不采用；职位首次启用仍必须已有一个确认后的职位需求版本。

职位需求版本按职位独立使用从 `v1` 开始的连续编号。确认草稿时，在同一数据库事务中分配下一编号、创建不可变版本、切换职位的当前版本并结束草稿；并发确认只能有一个成功，旧版本永久保留且不再作为当前版本。

确认事务先锁定对应 `jobs` 行，再按该职位现有最大版本号加一分配下一连续编号，不使用全局序列或独立可变计数器；数据库同时以 `(tenant_id, job_id, version_number)` 唯一约束兜底。事务回滚不会留下已消费号段，并发确认在职位行锁上串行化。

`jobs.current_requirement_version_id` 通过包含租户 ID、职位 ID 和职位需求版本 ID 的复合外键指向版本表，数据库强制当前版本属于同一租户和同一职位，不能只依赖全局唯一版本 ID。历史豁免职位可暂时为空，其他 `active` 职位由数据库门禁要求该受约束指针非空。

已有当前职位需求版本时，成员可以直接复制它创建新的职位需求草稿，手工修改后确认下一版本，不要求再次调用 OpenRouter。模型解析只负责把非结构化职位信息转为初稿，不成为版本修订的强制依赖。

成员可以放弃当前可编辑草稿；放弃只将草稿原子切换为 `abandoned`，不改变职位当前需求版本。`active` 或 `closed` 职位继续保留原版本，尚无确认版本的 `draft` 职位仍不能启用。

`draft`、`active` 和 `closed` 状态的职位均允许发起需求解析、编辑职位需求草稿并确认新版本；`archived` 是严格只读终态，只允许查看历史解析任务、草稿和职位需求版本，禁止创建、替换、编辑、升级或确认需求内容。

职位归档优先于正在进行的需求解析，不因解析任务未结束而阻止归档。归档事务使职位立即进入只读终态，并触发非终态解析任务取消；归档后到达的任何解析结果都不得创建或替换职位需求草稿。

引入职位需求版本时，数据库中已有的启用职位保持 `active` 并继续占用原活跃职位额度，但在确认首个职位需求版本前禁止发起匹配；迁移不伪造 `v1`，也不强制改变职位状态。此后草稿或已关闭职位的启用与重新启用都必须已有确认后的职位需求版本。

迁移为当时已有且没有职位需求版本的 `active` 职位设置不可由应用新增的 `legacy_requirement_exempt` 标记。数据库仅允许带该标记的历史职位在没有当前职位需求版本时继续保持 `active`；职位确认首个版本或从 `active` 关闭时永久清除标记，此后不得恢复。新职位永远不能获得该标记，所有未来启用和重新启用都由数据库强制要求当前职位需求版本存在。
