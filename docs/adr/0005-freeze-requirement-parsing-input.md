# 职位需求解析使用可修正的冻结输入快照

每次职位需求解析都绑定一份职位需求输入快照：由当时的职位描述和用户选中的职位材料生成，用户可在调用模型前修正抽取文本，提交后不再随来源变化。仅保存这份业务输入、来源标识与摘要以及提示词版本，不保存供应商请求中的完整组装提示词；相较于始终读取最新内容或自动拼入全部材料，这一选择能排除过期材料并复现模型实际收到的业务信息。

最终关联到确认职位需求版本的输入快照随职位历史长期保留；失败任务、被替换草稿或始终未确认的快照在 90 天后清除完整文本，仅保留来源标识、哈希、长度和任务事实。这样既保留已确认业务版本的来源证据，也不长期保存没有业务结果的废弃输入正文。

职位需求输入快照默认最多包含 100,000 个 Unicode 字符，实际限制随任务绑定的 LLM 配置版本记录。系统不自动截断或摘要；超限时要求用户取消选择部分职位材料或手工精简后重新提交，避免在不可见情况下删除关键条件或引入第二次模型解释。

输入修正界面按来源分段展示职位描述和每份选中职位材料，各段分别保留来源标识、文件哈希和用户修正后的文本；提交时按固定顺序与明确分隔组装给模型，而不保存一份失去来源映射的合并编辑文本。

被选中的职位材料必须在当前 RLS 租户内属于同一职位，并且状态为 `content_checked`。职位描述与材料都可独立成为来源分段；若材料提取文本为空，用户必须先为该分段填写非空修正文案，否则不能把它纳入解析任务。提交后的输入快照至少包含一个非空来源分段，后端不得将空来源静默发送给模型。

每个来源分段同时保留从职位描述或材料抽取得到的原始文本，以及实际发送给模型的成员修正文案，并记录执行修正的成员与时间，不要求填写修正原因。两份文本都属于职位需求输入快照正文，遵循相同的长期或 90 天分层保留规则；来源哈希以原始来源内容计算，发送内容另有独立哈希，不能相互覆盖。

发送内容在组装前只执行确定性规范化：Unicode 转为 NFC，换行统一为 `LF`；不折叠空白、不忽略大小写，也不改写标点。输入快照保存每个分段的规范化内容与哈希，模型来源证据使用规范化文本中的 Unicode 字符偏移，确保后端和历史重放使用同一坐标空间。

模型识别到不同来源对同一条件给出不能同时成立的内容时，必须输出来源冲突及相关来源，不得自行选择某一来源为准。职位需求草稿存在未解决来源冲突时禁止确认版本，用户必须明确选择、修改或移除相应条件。

确认后的职位需求版本永久保留原来源冲突、涉及来源、最终处理方式、处理成员和处理时间，而不只保存处理后的条件。冲突解决历史属于版本快照的一部分，后续版本不会改写早期版本的取舍依据。
