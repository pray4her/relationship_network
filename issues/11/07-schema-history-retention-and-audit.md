# 07 — 管理历史 Schema、保留策略与审计边界

**Parent:** GitHub Issue [#11](https://github.com/pray4her/relationship_network/issues/11) — `[MVP-10] 接入 OpenRouter 并完成职位需求解析确认`

**What to build:** 历史职位需求始终保持原有 Schema 语义，只有成员明确发起确定性升级时才转换为新草稿；有损项必须人工解决。系统按业务价值分层保留输入正文和长期历史，并通过 RLS、数据库权限及只增审计保证租户、Worker、平台和维护路径边界清晰。

**Blocked by:** 02 — 记录、诊断并清理 LLM 调用数据; 06 — 确认并修订不可变职位需求版本.

**Status:** ready-for-agent

## Acceptance criteria

- [ ] 历史草稿和职位需求版本默认继续绑定创建时的职位需求 Schema，不因当前 LLM 配置、提示词或 Schema 变化自动升级。
- [ ] 具有 `jobs:manage` 且租户可写的成员可以显式升级可编辑草稿；升级只使用有版本的确定性转换器，不调用 LLM 重新解释历史内容。
- [ ] 升级保留转换前 JSONB、转换器版本和逐项映射；不能无损转换的内容进入需要人工解决的明确状态，在解决前阻止确认。
- [ ] 提示词版本和职位需求 Schema 不匹配时在任何外部请求前拒绝；新任务的 Schema 只由当前 LLM 配置绑定的提示词推导，不维护独立可变指针。
- [ ] 关联到已确认职位需求版本的输入快照正文长期保留，以支持来源证据和历史重放。
- [ ] 失败任务、被替换草稿或始终未确认的输入快照在 90 天后清除原始及修正正文，但长期保留来源标识、哈希、长度、任务和清理事实。
- [ ] 职位需求解析任务、只增任务事件、通过校验的终态草稿、职位需求版本、LLM 调用核心、结果事件和元数据事件长期保留。
- [ ] 输入正文清理通过独立受限维护路径执行，只处理已到期且不关联确认版本的正文；普通 API 和 Worker 不能删除长期历史。
- [ ] 租户任务、事件、输入、草稿和版本始终执行严格 RLS；Worker 必须设置 `app.tenant_id`，不能自行切换平台 scope。
- [ ] 平台配置与平台调用的后台处理使用独立受限队列和显式平台上下文，不与普通租户 Worker 的权限路径混用。
- [ ] 只增任务事件、调用核心、结果事件、元数据事件和租户/平台审计表只授予应用角色 SELECT/INSERT；数据库拒绝 UPDATE/DELETE。
- [ ] 每次职位需求写操作和已认证业务拒绝都记录动作、关联标识、成员、时间和结果，不复制完整输入、草稿、版本、提示词或原始响应。
- [ ] 未认证请求和被 RLS 隐藏的跨租户探测不产生可泄露目标存在性的审计记录。
- [ ] 具有 `jobs:read` 的成员可以按来源和业务层级查看长期任务、草稿、版本与变更事实；租户界面不展示平台成本、提供方诊断或原始响应。
- [ ] 测试覆盖无损/有损升级、历史语义不变、提示词与 Schema 不匹配、90 天输入清理、长期保留、后台 scope 隔离、数据库权限、审计成功与失败路径。
