# 06 — 确认并修订不可变职位需求版本

**Parent:** GitHub Issue [#11](https://github.com/pray4her/relationship_network/issues/11) — `[MVP-10] 接入 OpenRouter 并完成职位需求解析确认`

**What to build:** 成员可以把已解决全部阻塞项的职位需求草稿确认成按职位连续编号的不可变职位需求版本，并原子切换职位当前版本。成员还可以在启用或关闭职位上准备后续版本，或复制当前版本进行无 LLM 修订；历史匹配引用不被新版本改写。

**Blocked by:** GitHub Issue #10; 05 — 审阅和维护职位需求草稿.

**Status:** ready-for-agent

## Acceptance criteria

- [ ] 确认要求 `jobs:manage`、可写租户、匹配的预期草稿 revision、非空研究主题查询以及全部来源冲突已解决。
- [ ] 确认事务先锁定职位行，以该职位现有最大版本号加一分配从 v1 开始的连续编号，并由数据库唯一约束防止并发重复。
- [ ] 同一事务创建不可变职位需求版本、切换职位当前版本指针并终结草稿；回滚不留下已消费编号或部分状态。
- [ ] 数据库通过包含租户、职位和版本标识的复合外键强制当前版本属于同一租户和职位，不能只依赖全局版本标识。
- [ ] 职位需求版本保存通过 Schema 校验的完整 JSONB、来源证据、原始模型事实、人工修改事实、来源冲突及处理记录；应用角色不能更新或删除版本。
- [ ] `draft`、`active` 和 `closed` 职位均可确认新版本；启用职位确认新版本不改变其状态或活跃职位额度，只影响未来匹配，历史匹配继续引用旧版本。
- [ ] 新职位首次启用及关闭职位重新启用必须存在当前职位需求版本，并由数据库门禁兜底。
- [ ] 迁移时已经启用但没有版本的职位保持启用并继续占用原额度，但禁止匹配；只有迁移能授予历史豁免。
- [ ] 历史豁免在首次确认版本或职位关闭时永久清除，应用代码不能创建或恢复豁免，未来重新启用必须有版本。
- [ ] 已有当前版本的成员可以复制其完整业务快照创建新的可编辑草稿，不发起 OpenRouter 调用，不创建 LLM 调用记录。
- [ ] 复制后的修改和确认形成新版本并引用来源版本；历史版本始终保留且不原地重新启用或修改。
- [ ] 具有 `jobs:read` 的成员可以查看当前版本和完整版本历史；归档职位仍可查看任务、草稿和版本，但禁止复制、编辑、升级或确认。
- [ ] 并发确认只能有一个成功；失败方得到明确乐观并发冲突，不产生额外版本或错误当前指针。
- [ ] 确认、复制、启用门禁拒绝和并发冲突写入不含完整版本内容的租户审计事件。
- [ ] 真实 PostgreSQL 并发、RLS、前端和浏览器测试覆盖 v1/v2 编号、原子切换、复合外键、不可变权限、启用门禁、历史豁免、启用中修订、手工复制和归档历史。
